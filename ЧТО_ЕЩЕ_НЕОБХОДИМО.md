# Что ещё необходимо: честный разбор остатка

Дата: 2026-11-04. Версия набора: 2.2 + исправленные консольные скрипты.
Проверок: 209 (94 + 59 + 19 + 37), плюс A/B на 7 сценариев.

Отвечаю по трём уровням: (1) что я закрыл прямо сейчас, пока отвечал на
вопрос; (2) что нужно от вас, потому что без этого двигаться нельзя;
(3) что можно доделать дальше, с оценкой пользы и цены.

---

## 1. Закрыто в этом заходе: консольные скрипты отставали от GUI

Проверяя «что ещё», я нашёл в скриптах **тот же дефект**, который дважды
исправлял в GUI:

| Файл | Было | Стало |
|---|---|---|
| `linux/flashcard.sh` | `flashcp -v` после подтверждения «Стереть карту и записать» — **хвост карты не стирался** | сначала `flash_erase 0 0`, затем `flashcp`; `MTD_KEEP_TAIL=1` для прежнего поведения |
| `pcmcia_flash.sh` | то же самое в пункте меню 6 | `flash_erase 0 0` перед записью |
| оба | не проверяли, смонтирована ли карта | `check_unmounted()` по `/proc/mounts` |
| оба | не смотрели на write-protect | `check_writable()` по флагу `MTD_WRITEABLE` (0x400) |
| `flashcard.sh` | снятие образа без проверки места | `check_space()` требует 2 копии |
| `pcmcia_flash.sh` | тест записи писал файл размером с карту в `/tmp` без проверки | проверка свободного места до создания |
| оба | — | `shellcheck -S warning`: чисто (было 1 замечание) |

Доказательство — поведенческие тесты `tests/test_scripts.py` (37 проверок):
скрипты запускаются на заглушках, и проверяется **журнал реальных вызовов**
(`flash_erase` вызван, и именно раньше `flashcp`; хвост карты 0xFF; при отказе
от подтверждения карта не тронута; меню из stdin доходит до записи).

Показательный момент: первая попытка правки `erase` и `ftl` в
`flashcard.sh` не сработала (шаблон не совпал), и это выяснилось только
тестом, а не чтением диффа. Ровно поэтому тесты на поведение, а не на текст.

## 2. Без вас дальше нельзя (это блокирует всё остальное)

### 2.1. Прогон на реальном ноутбуке — главный оставшийся риск

Все 209 проверок идут на файле-заглушке. Ни одна не проверяет:
pcmciamtd на TI PCIxx21, тайминги, реальный Vpp, ошибки стирания конкретной
микросхемы, поведение при нестабильных контактах. Это не «для галочки»:
именно там живут проблемы, которых не бывает в эмуляции.

Что нужно: вывод трёх команд с ноутбука (или скриншоты окна).

```bash
sudo python3 pcmcia_gui.py --doctor            # вся диагностика
sudo ./pcmcia_gui.py   # далее: «Идентификатор (CIS)» -> «Проверить слот»
                       #        -> «Тест записи (0xFF)» -> «Прочитать карту в файл»
```

Уже подготовлен чек-лист (см. `ЧЕКЛИСТ_НА_ЖЕЛЕЗЕ.md`): 12 шагов, на каждом
написано, что должно быть на экране и что означает отклонение. Пришлите
результат — разберу по строкам.

### 2.2. Какая карта у вас в руках

От этого зависит, возможна запись вообще:
- **Intel Series 2 (28F008SA)** — нужно 12 В, в ноутбуке их нет → только чтение;
- **Series 2+ / Value 100 / AMD / Sharp** — пишется от 5 В.

Определяется по CIS (`PRODID_2`). Если карта 12-вольтовая, все усилия по
записи бессмысленны, и это лучше узнать до экспериментов.

### 2.3. Что важнее: одна карта или парк карт

Если карт несколько и образы нужно хранить/сравнивать — имеет смысл каталог
образов с индексом. Если карта одна — не нужно, лишняя сложность.

## 3. Что можно доделать дальше (по убыванию пользы)

### A. Автотест на живом железе (высокая польза, средняя цена)

Скрипт `tests/hw_smoke.sh`, который на ноутбуке сам проходит безопасную
последовательность: `info` → чтение первых 64 КиБ → запись в **последний**
блок (данные в начале не трогаются) → сверка → восстановление → отчёт
в файл. Позволяет отличить «карта не пишется» от «программа врёт» без
риска потерять дамп. Цена: ~150 строк bash + аккуратность с dry-run.

### B. Сверка образа с картой «умнее» (средняя польза, низкая цена)

Сейчас сверка идёт с начала файла. Полезно:
- сверять с любым смещением (образ, снятый с `--offset`);
- отдельно сообщать «карта чище файла» (лишние 0xFF) — частая ситуация
  после записи короткого образа.

### C. Проверка образа до записи (средняя польза, низкая цена)

Сейчас программа пишет любой файл. Перед записью стоит:
- показать первые 16 байт и «похоже на файловую систему / на пустоту / на мусор»;
- отказываться писать образ, целиком состоящий из 0x00 (частая ошибка —
  записали не тот файл);
- предупреждать, если образ побайтово совпадает с текущим содержимым карты
  (запись не нужна).

### D. Работа с FTL-картой как с диском (средняя польза, средняя цена)

Сейчас есть только `ftl_format` + `mkfs.vfat`. Не хватает:
- монтирования с проверкой `fsck.vfat`;
- копирования файлов внутрь смонтированной карты из GUI (сейчас только через
  файловый менеджер);
- корректного `umount` перед выдёргиванием карты (сейчас это делает
  пользователь вручную — типичный источник потери данных).

### E. Диагностика «карта не появилась» (низкая цена, заметная польза)

Сейчас программа печатает список причин текстом. Можно автоматизировать:
проверить `lspci` на наличие моста, `dmesg` на строки `pcmciamtd`, наличие
`/sys/class/pcmcia_socket`, и выдать **одну** наиболее вероятную причину
с конкретной командой для проверки. Экономит переписку.

### F. Хранение и сравнение образов (низкая польза для одной карты)

Индекс снятых образов (дата, карта, md5, размер), быстрое сравнение двух
образов с картой расхождений. Имеет смысл только если образов много.

### G. Упаковка в .deb (низкая польза, средняя цена)

`pcmcia-flash-tool_2.2_all.deb` с ярлыком меню и зависимостями. Удобно при
переустановке системы, но набор и так ставится копированием папки.

## 4. Чего делать не надо (и почему)

- **Поддержка 12-вольтовых Series 2 на запись.** Ограничение железа: 12 В на
  pin 18 в этом ноутбуке не разведены. Никакой код этого не изменит.
- **Сборка модуля `pcmciamtd` с `CONFIG_MTD_PCMCIA_ANONYMOUS`.** Нужна только
  для карт совсем без CIS — редкий случай. Собирать сейчас = тащить
  заголовки ядра и рисковать несовпадением версии без необходимости.
- **Поддержка Windows Vista+.** Драйвера linear flash там нет; обходной путь
  (live-Linux) уже описан в README.
- **Автоопределение «правильного» Vpp по модели карты.** Ошибка в этом месте
  потенциально вредит карте; ручной выбор из двух безопасных значений
  (5.0 / 3.3 В) с запретом остальных — правильнее.

## 5. Как я предлагаю двигаться

1. Вы присылаете `--doctor` и результат шагов 1–4 чек-листа с ноутбука.
2. По результату я закрываю то, что реально стрельнуло (обычно это либо
   нестабильное чтение, либо карта 12 В, либо слот не поднялся).
3. Дальше по вашему выбору: A (автотест на железе), B/C (умная сверка и
   проверка образа), D (FTL как диск), E (диагностика «карта не появилась»).

Если железа под рукой нет — самый полезный из недорогих шагов сейчас B+C:
они уменьшают шанс испортить карту неправильным или обрезанным образом.
