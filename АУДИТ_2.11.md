# Аудит проекта PCMCIA flash kit 2.11.0

Дата: 2026-11-05 · Объём: 8 268 строк кода в 9 файлах · Платформы: Debian 12 i386 (ноутбук), Windows 10/11 PowerShell 5.1 (пульт)

Аудит сделан **по коду и по живым логам**, не по описаниям. Использованы: `shellcheck`, `pyflakes`, `bandit`, сверка с исходниками ядра (`rsrc_nonstatic.c`, `cistpl.c`), плюс прогоны на подставном sshd (`127.0.0.1:2224`) и модели моста CardBus.

---

## 1. Что проект делает и где границы

Набор читает 16-битные карты PC Card напрямую через `/dev/mem`, когда ядро отказало карте в окне памяти (`cs: warning: no high memory space available!`), и управляет этим с Windows по ssh/scp.

| Возможность | Состояние | Оценка |
|---|---|---|
| Чтение CIS и паспорта карты | работает, подтверждено на живой карте | A |
| Снятие образа (двойное чтение + сверка) | работает, 4 МиБ за ~20 с до 2.10.0 | B+ (скорость исправлена в 2.11.0) |
| Размер карты | паспорт + повтор адресов + первый пустой участок | A− |
| Запись/стирание | только через mtd, и только если карта не требует Vpp 12 В | A (по честности), N/A по железу |
| ATA-карты (CF, Microdrive) | опознаются с 2.10.0 | B |
| CardBus/Card32 (32-бит) | не поддерживаются, честно сообщается | — |
| Пульт Windows → ноутбук | ssh/scp, ключ, живой вывод | A− |

Главная архитектурная удача: **всё управление идёт с Windows**, на ноутбуке ничего не запускается руками. Это ровно то, что просил заказчик, и это выдержано во всех путях (кроме аварийных подсказок).

Главный архитектурный риск: набор читает карту **мимо ядра**, значит он конкурирует с `yenta_socket` за регистры ExCA. Это не лечится кодом до конца — лечится порядком действий (`modprobe -r yenta_socket`) и проверками, которые теперь есть.

## 2. Найденные дефекты

### 2.1. Узкое место чтения — размер окна, а не mmap (исправлено в 2.11.0)

В версии 2.8.9 я поставил `WIN_CHUNK = 1 МиБ` и написал в аудите, что «дело было в количестве mmap». Это было **неверно**: `mmap` отображает окно моста, а карту за один заход видно только на `CIS_WINDOW = 4 КиБ`. То есть на 4 МиБ делалось 1024 перестановки окна (запись 5 регистров ExCA) на проход — 2048 при двойном чтении. Отсюда 0.40 МиБ/с.

```
было:  READ_SPAN = 4096      → 1024 захода на 4 МиБ
стало: READ_SPAN = 64 КиБ    → 64 захода на 4 МиБ (в 16 раз меньше)
```

Регистры `I365_MEM0_START/STOP` хранят **номер страницы** в младших 12 битах, поэтому окно до 16 МиБ кодируется без изменений формата. Взят безопасный шаг: 64 КиБ = 16 страниц при окне моста 64 МиБ. Есть `--span 4096` для отката, если на каком-то мосте большой заход не сработает.

**Не проверено на живой карте** — проверено моделью моста и тестом S24p. Это надо подтвердить первым же живым чтением.

### 2.2. Чтение не с начала страницы возвращало начало страницы (исправлено в 2.10.0)

```python
page_off = card_off & (PAGE - 1)   # это добавлено в 2.10.0
read_mem(data, win["start"] + page_off, length)
```

До этого окно ставилось на `card_off & ~0xfff`, а смещение внутри страницы игнорировалось. На linear flash не проявлялось (всё читалось с 0x0000, 0x1000, …), но **паспорт ATA-карты лежит по 0x200** — он не прочитался бы никогда. Дефект был скрыт, пока не появилась поддержка ATA.

### 2.3. Размер карты брался из окна моста (исправлено в 2.9.0)

Живой прогон снял 64 МиБ вместо 4 МиБ за 340 секунд: алгоритм «размер = период повторения адресов» не работает, если карта не отражает неотключённые линии (за концом читались нули). Правильный ответ уже был в паспорте. Теперь приоритет: паспорт → повтор → первый пустой участок → окно (с предупреждением).

### 2.4. Кодировка (исправлено в 2.8.8), нестабильное чтение (2.9.1), ошибка `df` в locale (2.9.1)

- UTF-8 с ноутбука + cp866-консоль Windows = «кракозябры». Лечится с двух сторон.
- Нестабильный ответ карты не ловился: два прохода могли совпасть случайно. Теперь правило двух из трёх, и первым читается первый блок каждого захода — ошибка видна в первые секунды.
- `[: 1,42826e+11: ожидается целочисленное выражение` — `df` в locale отдаёт значение с запятой; проверка свободного места молча отваливалась. Теперь `LC_ALL=C` + только целые числа.

## 3. Аудит кода: линтеры

### shellcheck (`-S warning`)

```
pcmcia_ctl.sh:105: ST_CIS_RC appears unused                      [SC2034]
pcmcia_ctl.sh:195: Declare and assign separately (masking rc)    [SC2155]
pcmcia_ctl.sh:226: IMG appears unused                            [SC2034]
run_remote.sh:69:  sudo doesn't affect redirects                 [SC2024]
planb.sh:36:       eval negates the benefit of arrays            [SC2294]
```

Оценка: скрипты в приличном состоянии. `SC2024` (`sudo cmd > file`) — реальный класс ошибки: редирект выполняется от пользователя, а не от root. В `run_remote.sh` это может привести к «тихо не записалось». `planb.sh` с `eval` — потенциальная инъекция, но файл вспомогательный.

### pyflakes

```
pcmcia_direct.py:1209 local variable 'base' is assigned but never used
pcmcia_direct.py:1558 'collections' imported but unused
pcmcia_direct.py:2029 local variable 'suspect' assigned but never used
pcmcia_direct.py:2231 local variable 'first' assigned but never used
```

Мёртвый код: косметика, но `suspect` показывает, что результат проверки «окно занято драйвером» **не используется в решении** — только печатается. Это недоделка, а не стиль (см. §5.2).

### bandit

| Находка | Оценка |
|---|---|
| `hashlib.md5` (3 места) | ложная тревога: md5 здесь для целостности образа, не для безопасности. Но **sha256 добавлен** — для настоящих данных он уместнее |
| `subprocess` с `shell=True` в `pcmcia_gui.py` | проверил: сборка строки из фиксированных частей, пользовательский ввод не подставляется. Тем не менее `shell=True` тут не нужен |
| `except: pass` ×8 в GUI | осознанно (Tkinter), но в 3 местах скрывает реальные ошибки |
| hardcoded `/tmp` | в GUI временный файл предсказуемого имени — теоретический TOCTOU при многопользовательской системе. На этом ноутбуке один пользователь, но `tempfile.mkstemp` был бы правильнее |

Ничего критичного. Ни одной находки класса «выполнение произвольного кода извне».

## 4. Аудит ssh/scp

### Что сделано правильно

- `StrictHostKeyChecking=accept-new` вместо `no` — компромисс разумный: первый контакт доверяет, смена ключа ловится (`ssh-keygen -R`).
- `IdentitiesOnly=yes` при указанном ключе — не перебирает чужие ключи из агента.
- `NumberOfPasswordPrompts=1` — не зацикливается на пароле.
- `ServerAliveInterval=15` — не висит на мёртвом соединении.
- Порт разведён правильно: `-p` у ssh, `-P` у scp (классическая ловушка).
- Ключ создаётся `rsa 2048` с обходом бага PowerShell 5.1 (пустой `-N ""`).
- Обмен файлами — только `scp`, как требовал заказчик; потоковых `tar | ssh` нет.
- Проверка md5 **на обеих сторонах** до и после записи — правильно.
- Пароль не передаётся и не хранится нигде: только интерактивный ввод ssh.

### Пробелы

| # | Проблема | Риск | Что делать |
|---|---|---|---|
| S1 | **Нет `sha256` при передаче образов** — только md5 | средний (для 4 МиБ данных md5 достаточно, но для «настоящих данных» лучше sha256) | сделано в 2.11.0: sha256 печатается рядом с md5 |
| S2 | **Нет `AcceptEnv`/`SendEnv` контроля и нет `-o ForwardAgent=no -o ForwardX11=no`** | низкий: агент/X11 не пробрасываются по умолчанию, но явный запрет — гигиена | добавить в `$common` |
| S3 | **Нет `ControlMaster`** — на каждый шаг новое TCP-соединение и новый ключевой обмен | низкий (по ssh это доли секунды), но на 5 шагах умножается | `ControlMaster=auto`, `ControlPath`, `ControlPersist=60` |
| S4 | **`StrictHostKeyChecking=accept-new` несовместим с очень старыми OpenSSH (< 7.6)** | низкий: на Windows 10/11 свой OpenSSH ≥ 7.7 | ловить ошибку и откатываться на `ask` |
| S5 | Пароль root по ssh — рабочий путь. `PermitRootLogin` настраивается на ноутбуке, набор это объясняет, но **не предупреждает, что вход root по паролю — худший из вариантов** | средний, организационный | в инструкции: сначала ключ, пароль — только на один запуск `add_key.ps1` |
| S6 | `known_hosts` Windows общий с остальными ssh-сессиями пользователя | низкий | по желанию: отдельный `UserKnownHostsFile` |

### Отдельно про «нет `sftp` на ноутбуке»

Современный `scp` по умолчанию идёт через `Subsystem sftp`. Если на ноутбуке sftp выключен — файлы не копируются вообще. Набор это ловит и печатает готовую команду включения. Альтернатива для старых серверов — `scp -O` (старый протокол). **Стоит добавить автоматический откат на `-O`**, если видим `subsystem request failed`: это избавит от ручной правки `sshd_config` на чужой машине.

## 5. Аудит PCMCIA-части

### 5.1. Что соответствует документации и коду ядра

- Читается **CIS из attribute memory**, а не «по адресу окна» — с проверкой `I365_MEM_REG`.
- Копирование подхода `yenta_set_mem_map`: регистры `START/STOP/OFF` + бит 16-битной шины `0x8000`.
- Окно выключается до правки регистров и восстанавливается в `finally` — правильно, иначе оставляем мост в чужом состоянии.
- `mem_for_addr` умеет уходить с `/dev/mem` на `resourceN` из sysfs при `STRICT_DEVMEM` — верное решение для `iomem=relaxed`-случая.
- Размер по `CISTPL_DEVICE` считается как в `parse_device()` ядра: `((p>>3)+1) * (512 << (scale*2))`.
- `0xFF` и `0x00` в attribute memory различаются и трактуются по-разному — грамотно, это разные физические ситуации.

### 5.2. Пробелы

| # | Проблема | Оценка |
|---|---|---|
| P1 | **Чтение не защищено от прерывания/выгрузки драйвера посреди работы.** Если `yenta_socket` переставит окно между нашими заходами, получим мусор. Двойное чтение это ловит, но только на повторе | средний |
| P2 | **`suspect` (занято ли окно драйвером) вычисляется, но не влияет на решение** — только печатается. Надо: при `suspect=true` не снимать образ, а предлагать `modprobe -r yenta_socket` | недоделка |
| P3 | **Запись мимо ядра отсутствует — и это правильно.** Но в коде остались `Mem(writable=True)` для ExCA; на карту через common memory запись не идёт нигде. Проверено: ни одного `write` в common memory | соответствует замыслу |
| P4 | **Нет проверки на 3.3 В карты** (`CISTPL_CFTABLE`/`Vcc`): 5 В карта в 3.3 В слоте читается, но с ошибками | низкий |
| P5 | **Vpp 12 В определяется по подстроке `AMD|Am29|Series 2|Intel` в тексте паспорта** — эвристика. Формально надо смотреть `CISTPL_CFTABLE` (биты Vpp1/Vpp2) | средний: ложное «нельзя писать» безопасно, ложное «можно» — опасно. Сейчас ошибка возможна только в сторону запрета |
| P6 | **ATA: нет IDENTIFY DEVICE**, объём диска не читается (только паспорт). Нужен I/O-режим окна — без живой карты делать вслепую нельзя | открыто |
| P7 | **Нет таймаутов на чтение карты.** Если карта «залипла», процесс будет читать бесконечно (при зависшем мосте это возможно) | низкий-средний |
| P8 | **`--trim` работает только по явному размеру**, автоподрезки по паспорту нет: если образ больше карты, набор подсказывает команду, но не делает | косметика |
| P9 | **Нет проверки «карта вынута во время чтения»** — на живом железе это даёт мусор, который ловится только двойным чтением | средний |

### 5.3. Вопрос производительности: почему 0.40 МиБ/с — это медленно

Для сравнения: `mtd_debug read` с `/dev/mtd` на таком же ноутбуке обычно даёт 1–3 МиБ/с, то есть наш путь был медленнее в 3–7 раз. Причина не в карте (Am29F016 отдаёт байт за ~90 нс, теоретически это десятки МиБ/с), а в перестановке окна: 5 записей в ExCA + `mmap` на каждые 4 КиБ.

Расчёт после 2.11.0: 64 захода на 4 МиБ × 16 страниц = те же 1024 страницы, но **системных вызовов в 16 раз меньше**. Ожидаемое ускорение — от 3 до 10 раз, то есть 4 МиБ за 2–6 с. **Это гипотеза, которую надо подтвердить живым прогоном.**

Что можно сделать дальше (если понадобится): карта видна в окне целиком, если размер окна ≥ размера карты — то есть 4 МиБ карту можно отобразить **одним** окном 4 МиБ и читать без перестановок вообще. Ограничение: окно моста должно это позволять (у пользователя 64 МиБ — позволяет), а `START/STOP` должны поддерживать такой размер. Это следующий шаг оптимизации, но он требует живой проверки.

## 6. Аудит надёжности и честности выводов

Сильная сторона проекта — **набор не врёт**. Проверено по коду:

- нет `/dev/mtd` → «запись невозможна», а не «попробую и посмотрим»;
- Vpp 12 В → отказ с объяснением, без попыток;
- attribute memory пуста → три разных диагноза для `0x00`, `0xFF`, «мусор»;
- образ больше паспорта → предупреждение и команда обрезки;
- два чтения разошлись → ошибка, образ не сохраняется;
- порт/сеть → «это не носитель», образ не снимается.

Слабости:

- **Диагноз «контакты» давался без проверки состояния окна** (исправлено в 2.9.1: печатаются регистры ExCA и наличие `yenta_socket`).
- **Приоритет советов был неверным**: сначала «протрите ластиком», потом «проверьте драйвер». Теперь наоборот.
- **Эвристика Vpp** может включиться на карте, которая на самом деле пишется (см. P5).
- **Ложное «окно читается»**: проверка `card_window_check` считает неоднородное содержимое признаком живой карты. Мусор от занятого окна тоже неоднороден.

## 7. Аудит документации и «устаревания»

Это оказалось **самой слабой частью проекта**, и именно она съедала время пользователя.

| Файл | Проблема |
|---|---|
| `ИНСТРУКЦИЯ.md` | 2 000+ строк, описывает версию 2.4 и меню на ноутбуке; числа тестов менялись 5 раз (656 → 692 → 714 → 727 → 735 → 745 → 759) |
| `README_FIRST.txt` | «Версия набора: 1.0 (2026-11-04)» — прямо неверно |
| `SSH_РАБОТА.txt`, `ПОРЯДОК_ЗАПУСКА.txt`, `ЧТО_НУЖНО_НА_WINDOWS.txt`, `КАК_ПЕРЕДАЮТСЯ_ФАЙЛЫ_scp.txt`, `ЧТО_ДЕЛАТЬ_*.txt` | 6 файлов с пересекающимся содержимым; часть описывает старые точки входа (`remote_collect.ps1`, меню на ноутбуке) |
| `AUDIT_2.1.txt`, `AUDIT_2.2.txt`, `AUDIT_2.4.txt` | 3 «аудита» на 180 КБ; читаются как рабочий журнал, а не как документ |
| `MD5_АРХИВА.txt` | переписывается каждый выпуск вручную — источник ошибок |

Пользователь трижды за сессию получал **не тот путь запуска** (`.\RUN.ps1 info` до появления `-Action`, старая копия в `for-windows`, «файлы устаревшие»). Причина не в коде, а в том, что **документации пять штук и они расходятся**.

Рекомендация: один `README.md` (что делать), один `ЖУРНАЛ.md` (почему так сделано), остальные файлы — либо в архив, либо в `docs/`. Числа тестов и версию генерировать скриптом при сборке, а не править руками.

## 9. Оценки по разделам

| Раздел | Оценка | Обоснование |
|---|---|---|
| Архитектура | B+ | единственная правильная идея (Windows управляет, ноутбук исполняет), но чтение мимо ядра — вечная конкуренция с драйвером |
| Код PCMCIA | A− | соответствует модели ядра, честные отказы; минусы — эвристика Vpp, нет таймаутов |
| Код PowerShell | B | много обходов багов PS 5.1, которые задокументированы; `RunSshLive` сделан аккуратно, но это 100 строк там, где хватило бы `ssh` с `TERM=dumb` и `-tt`-альтернативы |
| Код bash | B+ | shellcheck почти чистый; `sudo … > file` и `eval` — реальные, но второстепенные |
| ssh/scp | A− | ключи, `IdentitiesOnly`, md5 на обеих сторонах; нет `ControlMaster`, нет отката `scp -O` |
| Обработка ошибок | A− | лучшая часть проекта: ни одного «попробую и посмотрим» |
| Производительность | C → B+ (2.12.0) | было 0.40 МиБ/с → заход 4 МиБ: одна перестановка окна на проход; на железе ещё не подтверждено |
| Документация | D | 6 пересекающихся файлов, устаревшие версии и числа |
| Тесты | B+ | ~870 проверок, A/B-набор; нет тестов производительности и идемпотентности |
| Безопасность | B+ | нет инъекций; paranoia-настройки ssh неполные; пароль root по ssh остаётся вариантом |

**Итоговая оценка: B+ (хорошо, с известными границами).** Для утилиты, работающей с «железом, которое ядро не поняло», это честный результат: код не врёт, ошибки превращаются в тесты, но документация отстаёт от кода, а производительность только что исправлена и ещё не подтверждена.

## 10. План работ по приоритетам

### Сделано в 2.11.0

1. `READ_SPAN` 4 КиБ → 64 КиБ (+`--span` для отката) — главное узкое место.
2. `flock` на файл образа: два одновременных запуска переставляют одно и то же окно и оба получают мусор.
3. `sha256` рядом с `md5` в отчёте об образе.
4. Тест S24p (8 проверок).

### 2.14.0: запись без драйвера (то, чего не хватало с самого начала)

Свой драйвер писать не пришлось: не хватало не драйвера, а выполнения команд
микросхемы через уже работающее окно. Теперь `pcmcia_direct.py --write-probe`
и `--write <образ>` пишут JEDEC-командами (AA/55, A0, 80/30, опрос DQ7/DQ5),
с обязательной пробой одного сектора и возвратом его данных. Подробно:
AUDIT_2.4.txt §52. Тесты: 856.

### 2.15.0: разные микросхемы в картах

2.14.0 была написана «под Am29F016»: сектор 64 КиБ, команды байтом, два чипа,
JEDEC. По документам C-ONE Series-II (карты на Intel 28F008SA) и Kontron
PC/104-PCMCIA-1 (Vadem VG-469) видно, что это лишь один из вариантов: сектор
бывает 16 и 128 КиБ, команды - словом (Intel CUI со статусным регистром вместо
DQ7/DQ5), микросхем в карте - от 1 до 8, Vpp - 5 или 12 В.

Сделано: `protocol` в таблице микросхем, ветки Intel CUI (20h/D0h, 40h, 70h,
50h), раскладка по N чипам, сектор карты = сектор чипа x число чипов, опрос
90h словом для Intel, ключ `--identify-chip` (и пункт 11 пульта, `chip` в
RUN_CTL.ps1) - опрос без записи, предупреждение про 12 В по имени микросхемы.
Подробно: AUDIT_2.4.txt §53. Тесты: S26 (35 проверок) и P2-21.

По дороге найдены и исправлены пять настоящих дефектов, в том числе опрос
идентификатора без разблокировки и чтение байта до команды FF (см. §53).

Оценка PCMCIA после 2.15.0: A− (на железе по-прежнему не подтверждено).

### 2.13.0: снято ложное утверждение про Vpp (главная содержательная правка)

Оценка «запись на вашей карте невозможна, нужен Vpp 12 В» была получена не из
даташита, а из эвристики по слову AMD в паспорте. По документации AMD Am29F016
- семейство 5.0 V only, 12 В ему не нужны. Подробно: AUDIT_2.4.txt §51.

Изменено: vpp_need() в pcmcia_direct.py, разбор строки вместо grep в
pcmcia_ctl.sh, ПРОБА ОДНОГО СЕКТОРА перед полной записью, профиль pcmciamtd
как альтернатива своему драйверу, переписаны все тексты про Series 2/Am29Fxxx.
Тесты: 802 проверки.

Оценка PCMCIA после правки: A− → A− (не A, пока запись не подтверждена на
железе: доказательства нет, и набор обязан это говорить).

### Сделано в 2.12.0 (по результатам этого аудита)

1. **P2 закрыт**: `suspect` (окно выключено/занято драйвером) теперь **останавливает** работу до советов про контакты, и в `--cis`, и в `--read`. Раньше он только печатался.
2. **P7 закрыт**: таймаут застоя 60 с без нового байта → остановка с текстом «чтение встало, образ не сохранён».
3. Заход чтения поднят до 4 МиБ (`MAX_SPAN`): для 4 МиБ карты это **один заход**, то есть ни одной перестановки окна внутри прохода.
4. **S2/S3 закрыты**: `ForwardAgent=no`, `ForwardX11=no`, `ControlMaster=auto` + `ControlPath` + `ControlPersist=60`, закрытие мультиплексора через `ssh -O exit`.
5. **S6/«sftp» закрыт**: автоматический откат `scp -O`. Проверено живьём на стенде с выключенным `Subsystem sftp`.
6. `pyflakes` чистый (убраны `base`, `collections`, `first`, `win and dev`).

### Что аудит нашёл в самих тестах

Тест «два разных чтения отвергнуты» **зеленел зря**: модель портила каждое 5-е чтение, а после увеличения захода порча попадала в оба прохода одинаково — оба испорчены, но совпадают. Правило двух из трёх может вернуть испорченный блок, если карта врёт чередуясь. Тест ужесточён; ограничение зафиксировано честно: **если карта стабильно врёт одинаково, повторение это не поймает** — поэтому печатаются md5 и sha256, которые можно сверить с внешним источником.

### Следующее, по убыванию пользы

1. **Подтвердить скорость живым прогоном** (ваш `.\RUN.ps1 read`): ожидание 2–6 с вместо 20.9.
2. **P2: `suspect` должен влиять на решение** — при подозрении на занятое окно не снимать образ, а требовать `modprobe -r yenta_socket`. Полчаса работы.
3. **S5/S2/S3 по ssh**: явные `ForwardAgent=no`, `ForwardX11=no`, `ControlMaster` для 5 шагов, и **автоматический откат `scp -O`** при `subsystem request failed`.
4. **Документация**: один `README.md` + `ЖУРНАЛ.md`, версию и числа тестов генерировать при сборке. Это сэкономит пользователю больше времени, чем следующая оптимизация.
5. **P7: таймауты** на чтение (например, 30 с без прогресса → стоп с внятным текстом).
6. **Одно окно на всю карту** (4 МиБ за один заход) — потенциально ещё 5–10×; требует живой проверки.
7. **ATA IDENTIFY** и **разбор FAT с образа** — по мере появления живых ATA-карт.

### Чего делать не надо

- Не пытаться писать на карту мимо ядра. Без Vpp и таймингов это порча карты, и текущий отказ — правильное поведение.
- Не поддерживать CardBus без 32-битной карты в руках.
- Не «улучшать» эвристику Vpp в сторону разрешения записи: ошибка в эту сторону стоит карты.
