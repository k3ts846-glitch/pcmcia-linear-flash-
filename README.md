# PCMCIA FLASH KIT

Работа с линейной флеш-картой PCMCIA (linear flash) с обычной Windows-машины:
паспорт карты, снятие образа, запись, сверка, стирание. Сама карта стоит в
ноутбуке с Linux; пульт соединяется с ним по ssh и ничего там не устанавливает.

* Ни одного сценария PowerShell и ни одного `.cmd`: всё на Python 3.
* На ноутбук уходят только изменившиеся файлы набора.
* Запись выполняется командами микросхемы через окно моста, без драйверов.
* Понимает разные микросхемы: сектор 16/64/128 КиБ, команды байтом и словом,
  запись страницей 32 байта (AMD Am29F016/032), 5 В и 12 В на Vpp.

## Запуск без установки

```
python pcmcia-kit.pyw            окно пульта (или двойной щелчок по файлу)
python pcmcia-kit.pyw --text     текстовое меню
python pcmcia-kit.pyw --text info --dry-run
```

`pcmcia-kit.pyw` сам подключает папку `src`, поэтому настраивать нечего.
Форма `python -m pcmcia_kit` работает после установки пакета.

Требуется Python 3.9 или новее. Сторонних библиотек нет.

## Установка (необязательна)

Нужна, если хочется вызывать `pcmcia-kit` из любого каталога:

```
py -3 -m pip install .
pcmcia-kit info --host 192.168.0.71
```

Файлы набора (`pcmcia_direct.py`, `pcmcia_ctl.sh`) при этом остаются в
распакованной папке: запускайте из неё либо укажите `--kit-dir`.

## Запуск

```
python pcmcia-kit.pyw --text                     меню
python pcmcia-kit.pyw --text info                паспорт карты и вердикт
python pcmcia-kit.pyw --text read                снять образ и забрать к себе
python pcmcia-kit.pyw --text write -i card.bin   записать образ на карту
python pcmcia-kit.pyw --text verify -i card.bin  сверить файл с картой
python pcmcia-kit.pyw --text erase --yes         стереть карту
python pcmcia-kit.pyw --text chip                что за микросхема (не пишет)
python pcmcia-kit.pyw --text selftest            проверить набор (карта не нужна)
python pcmcia-kit.pyw --text key                 вход по ключу (без пароля)
```

После `pip install .` те же команды короче: `pcmcia-kit info`, `pcmcia-kit read`.

Двойной щелчок по `pcmcia-kit.pyw` открывает графический пульт: Windows
связывает `.pyw` с `pythonw.exe`, поэтому окно консоли не появляется.

Общие ключи: `--host`, `--user`, `--port`, `--key`, `--yes`, `--dry-run`,
`--image`, `--remote-path`, `--kit-dir`, `--full`.

## Что проверено, а что — только на модели

Набор проверяется двумя способами: автоматическими тестами на модели микросхем
(`tests/nor_model.py`) и, когда есть физическая карта, на живой карте
Centennial FL32M (2 × Am29F016, 4 МиБ). Ниже — честная матрица, чтобы было
видно, какие части кода подтверждены на железе, а какие только имитируются.

**Что исправлено в 2.17.1 и как это проверено.** Прежняя модель микросхемы
повторяла ошибки кода, поэтому зелёные тесты ничего не говорили о стирании.
Теперь и модель, и код сверены с даташитами (AMD/MX «Sector Erase Command
Sequence»: 555h/AAh, 2AAh/55h, 555h/80h, 555h/AAh, 2AAh/55h, **SA/30h**), с
`flashrom` (`issuecmd(0x30, page)`) и с ядром Linux
(`map_write(map, cfi->sector_erase_cmd, adr)`):

* `30h` теперь уходит **по адресу стираемого сектора**, а не в `0x555`
  (раньше всегда стирался сектор 0 — у карты это паспорт CIS);
* проверка геометрии перед записью **возвращает** снятый сектор, а не
  уничтожает его;
* таблица CFI читается по раскладке `include/linux/mtd/cfi.h` (0x2C — номер
  региона, 0x2D… — регионы); прежняя версия читала поля со сдвигом на байт;
* автоопределение по JEDEC ID сравнивает **числа**, а не строку «AMD»
  (раньше автоопределение не срабатывало никогда);
* у `Am29LV400B/LV800B` исправлена ёмкость (4 и 8 Мбит, а не МиБ), у
  `Am29F010` — 128 КиБ по 16 КиБ, у boot-чипов работа была запрещена
  (в 2.17.2 они поддержаны — см. ниже);
* если микросхема не знает Unlock Bypass (20h), запись сама уходит на A0h;
* в списке файлов для ноутбука были `planb.sh` и `pcmcia_flash.sh` — таких
  файлов нет, зато `planb.py` (его запускает `run_remote.py --planb`) на
  ноутбук не уезжал;
* таймаут ssh (`transport.run/run_live`) принимался параметром, но в
  `subprocess` не передавался — зависшее соединение ждало вечно;
* `pcmcia_ctl.py --json` без root печатал только просьбу про sudo, то есть
  разбирать было нечего; теперь строка `JSON {...}` есть всегда.

**Что нового в 2.17.2 — карта секторов boot-микросхем.**

До 2.17.2 набор отказывался работать с boot-чипами («неоднородная карта
секторов»). Теперь карта описана и используется везде: при стирании, в плане
записи, в резервных копиях секторов, в проверке геометрии и в отчёте.

* карта секторов одного чипа — `[(размер, число), …]` в `chips.json` и в
  `GEOMETRY`; bottom-boot `16K + 2×8K + 32K + N×64K`, top-boot — то же в
  обратном порядке (`Am29LV001B` — `8K + 2×4K + 7×16K`);
* `NorFlash.span(адрес)` и `spans(длина)` считают границы ПЕРЕСЕЧЕНИЕМ карты
  чипа с раскладкой байтов по чипам пары (16-битная карта: 8 КиБ на чип =
  16 КиБ карты);
* `30h` уходит по адресу сектора из карты — стирается ровно один сектор;
  проверено на модели, которая стирает именно сектор, куда попал адрес;
* CFI с несколькими erase-регионами больше не повод отказаться от чипа: из
  регионов собирается та же карта (`Am29F800BB`: `1×16K, 2×8K, 1×32K,
  15×64K`). Это снимает вопрос о ревизии: по JEDEC ID `58h`/`D6h` ревизию
  видно, но если микросхема молчит, CFI отвечает за неё;
* если ревизия неизвестна и CFI молчит (`--chip Am29F800`), набор честно
  отказывается с подсказкой «укажите BB или BT», а не выбирает наугад;
* в `GEOMETRY` монолита было 6 повторяющихся ключей (молча перекрывали друг
  друга) и у `28F016S5` — блок 128 КиБ вместо 64 КиБ (даташит Intel: 32 блока
  по 64 КиБ). Теперь обе реализации сверяются тестом: ёмкость и карта
  секторов у всех общих имён обязаны совпадать;
* по даташитам добавлены Fujitsu `MBM29F002TC/BC`, `MBM29F004TC/BC` и ST
  `M29F002BT/BB`, `M29F400BT/BB` (у ST коды `D5h`/`D6h` при вендоре `20h` —
  таблица вендоров теперь по вендору). Имена `M28F002`, `M28F004`,
  `M5M29F400` даташитами не подтверждаются и потому дают отказ с подсказкой,
  а не «умолчания как у Am29F016»;
* таблица JEDEC ID в `pcmcia_direct.py` приведена к сверенному реестру
  (`include/flashchips.h` flashrom + `jedec_probe.c`): `20h` — Am29F010,
  `57h/51h` — Am29F200B B/T, `ABh/23h` — Am29F400B B/T, `58h/D6h` —
  Am29F800B B/T, `D5h` — Am29F080, `BAh` — Am29F080B, `6Dh/EDh` —
  Am29LV001B B/T, `4Fh` — Am29LV040B, `3Dh` — Am29F017D, `41h` —
  Am29F032B. Прежние значения давали ёмкость с ошибкой до 8 раз (`0xAB` был
  «32 Мбит» вместо 4), а по ёмкости считается число чипов в карте.

Что по-прежнему **не** проверено на живой карте: реальное стирание/запись с
этими исправлениями, VPP слота, поведение CFI у конкретной карты. Об этом
набор пишет в отчётах, а не молчит.

**Что нового в 2.17.3 — сверка таблицы микросхем с даташитами.**

Проверялись не только новые семейства, но и те строки, что стояли в таблице
«по умолчанию». Нашлось несколько ошибок, каждая из которых испортила бы
запись:

* **SST39SF040 / SST39VF040 (и 39VF010/020/080)**: сектор 4 КиБ, а не 64 КиБ
  (даташит SST DS25022A «uniform 4 KByte sectors», flashrom `sst.c`:
  `{4 KiB, 128}`). Со «стиранием по 64 КиБ» набор стирал бы в 16 раз больше
  нужного — по 15 чужим секторам. `SST39VF*` — 2.7–3.6 В, а не 5 В;
* **Intel 28F016S5** — микросхема **байтовая** («BYTE-WIDE Smart 5 FlashFile
  MEMORY FAMILY», 32 блока по 64 КиБ, 5 В). В монолите она стояла как
  `wide=True` и с 12 В, то есть команда CUI уходила словом. Буфер `25h/D0h`
  отключён: это команда AMD StrataFlash, в CUI Intel её нет — пишем по байту
  командой `40h`;
* **обозначения, которых нет в даташитах**: `AT29F040`, `AT29F040B`,
  `AT29F016`, `AT29F080` (у Atmel 5-вольтовый флеш с командами JEDEC — это
  `AT49F*`, а `AT29C*` — страничная запись без `30h`), `SST39VF016`,
  `SST39SF016` (у SST 16 Мбит называется `SST39VF160` и она x16),
  `28F002SA`, `28F004SA`, `M28F016S5`. Теперь это отказ с подсказкой, какое
  имя указать. Добавлены реальные байтовые `28F004S5` (8×64 КиБ) и `28F008S5`
  (16×64 КиБ);
* **реестр JEDEC ID Intel** пересобран по двум независимым источникам
  (flashrom `flashchips.h` и ядро Linux `jedec_probe.c`): `A0h` 28F016SV,
  `A2h` 28F008SA, `A6h` 28F008S5, `A7h` 28F004S5. Прежние `A6h`→28F016SV,
  `B5h`→28F002SA, `B6h`→28F004SA были выдуманы (в ядре `B5h`/`B6h` — это SST
  `SST39SF010A/020A`), и реестр подтверждал сам себя: правки жили в двух
  копиях (`data/jedec_registry.json` и `jedec_registry.py`) и расходились.
  Теперь обе копии сверяет тест, а модель чипа берёт коды Intel из эталона;
* **опечатка в `--chip` больше не даёт умолчаний.** Раньше неизвестное имя
  молча получало «как у Am29F016»: сектор 64 КиБ, 2 МиБ. На boot-чипе первое
  же стирание задело бы `16K+8K+8K+32K`. Теперь — отказ с подсказкой;
* **AT29C010/020/040/512** честно помечены как неподдерживаемые: у этого
  семейства нет команды `Sector Erase 30h` (страница стирается сама при
  записи), поэтому стирать их нашим циклом нельзя.

**Что нового в 2.17.18 — `M28F008`/`M28F016` тоже Intel, и команды у них CUI.**

Следующие две строки из списка «не сверенных»: обе стояли в разделе ST и при
`volts=12` несли JEDEC-адреса `555h/2AAh` — то есть ту же ошибку, что была
у `28F256`/`28F512` и `D28F010`/`D28F020`.

| Источник | Что говорит |
|---|---|
| справочники компонентов | `M28F008` числится за **Intel**: «8 MBIT (1 MBIT x 8) FLASH MEMORY», 28 страниц; у Rochester то же описание с «Extended Cycling Capability» |
| Intel `28F008SA` (290429-008, уже был в таблице) | та же архитектура: 16 блоков по 64 КиБ, CUI + статусный регистр, 12 В на Vpp, команда байтом |
| Intel `MS28F016SV` | «Backwards-Compatible with VE28F008, **M28F008** and 28F016SA Command Set» — прямое подтверждение набора команд для `M28F008` |
| поиск точного имени `M28F016` | в перечнях Intel не нашёлся: 16-Мбит байтовые части семьи — это `28F016SA` и `MS28F016SV`/`VS28F016SV` (2 МиБ, блоки 64 КиБ, CUI) |

Итог правки:

* `M28F008`: `cmd` → `(0, 0)`, `protocol="intel"`, пометка «не сверено» снята;

**Что нового в 2.17.14 — карта из двух x8-чипов: команда каждому чипу.**

Аудит после 2.17.13 нашёл ошибку, которая на реальной 16-битной карте из пары
x8-микросхем ломала запись и стирание, а на модели выглядела успехом:

* **`_send()` посылал команду только в чип 0.** Байт команды дублировался лишь
  при `wide=True`, а у пары x8-чипов `wide=False`, поэтому `AAh`/`55h`/`80h`/
  `A0h`/`30h`/`20h` уходили в чип 0, а данные — в оба. Чип 1 команд не видел:
  **нечётные байты не программировались, сектор в чипе 1 не стирался**. При
  этом `card_geometry()` без паспорта карты по умолчанию считает `chips = 2`,
  то есть это не экзотика. Теперь команда идёт **каждому чипу** одним словом
  (байт команды дублируется в оба байта) — так это делают все три источника:
  Infineon KBA203626 («commands must be written in parallel to each 1x8 flash
  device … duplicated within the 2B word»), Linux MTD `cfi_build_cmd()`
  (размножает байт команды по чипам слова, адрес — `cmd_ofs * interleave`) и
  OpenOCD (dual flash: «command byte is sent to both chips»);
* **одиночный байт на паре чипов писать нельзя вообще.** После `A0h` микросхема
  ЖДЁТ данные, и чип, которому байт не достался, остался бы в этом состоянии —
  следующая `AAh` попала бы в него как **данные**. Поэтому на `chips > 1`
  запись идёт словом (`program_word`: свой байт + соседний как есть, запись в
  NOR умеет только 1 → 0, поэтому соседний не портится), и статус опрашивается
  по каждому чипу — он у пары не синхронизирован (Infineon KBA203626);
* **стирание сектора** теперь один цикл `80h`+`30h` словом на оба чипа (было
  «по циклу на чип», но `unlock()`/`80h` всё равно уходили только в чип 0), а
  стирание чипа — одна последовательность с `10h` словом;
* **`_intel_send()` для чипа 1 писал два байта со СДВИГОМ** (`chip_abs(…, 1)` =
  адреса 1 и 2): команда чипу 1 и та же команда чипу 0 по другому адресу. Для
  `70h` это переводило чип 0 в режим статуса, и чтение массива из чипа 0
  начинало отдавать байты статуса. Команда CUI действует на КАРТУ, поэтому
  пишется словом всегда по адресу чипа 0.

**Снова главное — модель.** Её командный автомат (и JEDEC, и у Intel) был ОДИН
на карту, поэтому все три ошибки выше она «подтверждала». Теперь состояние
ведётся **по чипам** (у каждого чипа свой командный регистр), добавлено
стирание чипа `10h` (раньше `chip erase` в модели вообще ничего не стирал),
и режим Unlock Bypass больше не сбрасывается на каждой записи — по даташиту он
держится до `90h/00h` или сброса. Раздел 21: 11 проверок (команды уходят обоим
чипам, данные словом, нечётный байт, сектор стирается в обоих чипах, один `30h`
на карту, стирание чипа, «данные без команды не программируются», «один `30h`
без `80h/AAh/55h` не стирает», `_intel_send` без сдвига, возврат в `idle`,
сеанс bypass на паре), всего **190 проверок**.

  циклов, ID: производитель `89h`, устройство `B4h`.

Отсюда правка: у строки появился флаг `ro` («в этом наборе только чтение»), и
`program_byte` / `program_page` / `erase_sector` / `erase_chip` отвечают отказом
с даташитной причиной вместо того, чтобы послать AMD-команды и «успешно»
дождаться DQ7 у нетронутого массива. Код `89h/B4h` добавлен в опознание, так
что `--identify-chip` теперь назовёт 28F010 по ответу самой микросхемы, а в
отчёте появится строка «только ЧИТАЕТСЯ».

**Что нового в 2.17.10 — по присланному Spec Update Intel (297796-007).**

Документ — Specification Update к даташиту 290597-005 «5 Volt FlashFile Memory;
28F004S5, 28F008S5, 28F016S5». Он подтверждает то, что в таблице уже стоит
(4/8/16 Мбит, **x8**, 5 В, однородные секторы 64 КиБ), а два пункта из него
дали настоящие правки в коде:

* **блокировка блоков.** Erratum #2: на 8- и 16-Мбит частях Intel прошивает
  master lock-bit на заводе, и **программно защиту снять нельзя** — нужны 12 В
  на RP#. Попытка писать в защищённый блок даёт WPPS=1 (бит 1 статуса), а наш
  код этот бит не различал и говорил просто «запись не удалась». Теперь ответ
  человеческий: «блок защищён (WPPS=1, block lock)… нужны 12 В на RP#, а слот
  их не даёт». Заодно после любого отказа чип возвращается в режим массива:
  раньше он оставался в режиме статуса, и следующее чтение отдавало байт
  статуса вместо данных (в тесте это вылезло как «байт не стёрт (0x82)»);
* **ширина команды.** Команда Intel должна доходить до каждого чипа пары ровно
  один раз. Прежнее `bytes([op, op])` на карте с **одним** чипом писало два
  байта в один чип: первый — команда, второй — уже данные (`0x40` как данные!).
  Теперь `bytes([op] * chips)`: на паре поведение прежнее, на одиночном чипе
  запись и стирание наконец работают.

Модель чипа тоже поправилась: она понимает WPPS и защищённые группы, а индекс
группы считала по 64 **байта** вместо 64 КиБ — из-за этого «защищённым»
оказывался соседний блок.

**Что нового в 2.17.9 — буферная запись Intel: E8h, счётчик, слово.**

Ветка буферной записи Intel (`page > 1`) не работала ни разу — у всех
Intel-строк таблицы `page=1` — и в ней было три ошибки сразу:

* команда `25h` — это **AMD** StrataFlash (JEDEC), в Intel CUI такой команды
  нет: даташиты Intel дают `E8h` (Write to Buffer);
* пропущен **счётчик N** = число байт минус один, который идёт вторым тактом;
* данные писались **побайтно**, а CUI принимает только слово.

Теперь последовательность как в даташите: `E8h` → `N` → N+1 слово данных →
`D0h` → опрос статуса. Команда и счётчик посылаются **одним словом на пару
чипов**: «каждому чипу» писать нельзя — второй такой же байт чип прочтёт как
счётчик (эту ошибку поймала модель, и на неё есть отдельная проверка). Плюс
отказ, если `page` больше 32 байт буфера.

Модель чипа этому научилась и стала придирчивее: неизвестная команда в CUI
теперь считается (`bad_cui_cmds`), поэтому старый протокол `25h` больше не
пройдёт молча.

По умолчанию буферный путь по-прежнему не включён: чтобы поставить `page=32`
Intel-строкам, нужен даташит конкретной части (`28F008S5`/`28F016S5`), а не
общее «у StrataFlash буфер 32 байта». Код готов и проверен на модели — включать
его вслепую было бы ровно той ошибкой, с которой начинался этот аудит.

**Что нового в 2.17.8 — шестой заход: части, которых у AMD не было.**

* **`Am29F033`** — такого 5-вольтового чипа нет. В селекторе AMD в ряду
  32 Мбит стоит только `Am29F032B` (4M × 8, «64 uniform sectors of 64 Kbytes
  each»), а 32-Мбитная x16 часть у AMD трёхвольтовая — `Am29LV033C`. Строка
  теперь отказывает и называет оба настоящих имени;
* **`Am29F032`** и **`MBM29F033`** — обозначений без буквы `B` нет ни в
  селекторе AMD, ни в `flashchips.h`/`jedec_probe.c`; они помечены как
  «не сверено», но продолжают работать: параметры у них как у `Am29F032B`;
* добавлена **`Am29LV033C`** — 32 Мбит (4M × 8), 3,0 В, 64 × 64 КиБ. Это ровно
  та часть, которую стоит указывать вместо несуществующей «Am29F033» на
  3-вольтовых картах. Unlock Bypass у неё не подтверждён, поэтому работает
  штатная запись `A0h`.

**Что нового в 2.17.7 — пятый заход: ST M28F102 и 64-Мбит Am29DL640.**

* **ST M28F102** (даташит августа 1998): «1 Mbit (64Kb x16, **Bulk**) Flash
  Memory», 5 В питания, 12 В программирования, «Electrical CHIP ERASE in 1s» —
  это 64 Kword × 16 бит = **128 КиБ**, и поблочного стирания у него **нет
  вообще**. В таблице стояло 256 КиБ и шестнадцать секторов по 16 КиБ, то есть
  набор отправил бы `30h` чипу, который такой команды не знает. Теперь честный
  отказ: «стирание только целиком (bulk/chip erase, 12 В)»;
* **`Am29DL642`/`Am29DL643`** по-прежнему отказывают (ревизия не указана), но в
  объяснении теперь не догадка, а даташит: семейство Am29DL640D/G (23695C3,
  25693B) — четыре банка, **восемь 8-КиБ секторов снизу и восемь сверху**
  («Both Top and Bottom Boot»), между ними 126 по 64 КиБ. 8 × 8 КиБ + 126 ×
  64 КиБ + 8 × 8 КиБ = ровно 8 МиБ, и это проверяется тестом как арифметика.

Итого в таблице монолита 112 строк, из них 29 — с честным отказом вместо
догадки; 15 строк помечены «не сверено с даташитом».

**Что нового в 2.17.6 — четвёртый заход: семейство Am29DL и страж расхождений.**

Даташит AMD 21534d (Am29DL322D/323D/324D): «32 Megabit (4 M x 8-Bit/2 M x 16-Bit)
CMOS **3.0 Volt-only**, Simultaneous Operation». В таблице эти строки стояли как
«5 В, однородные 64 КиБ», а на самом деле у них **восемь boot-секторов по 8 КиБ**
(Table 2: Bank 1 = 8 × 8 КиБ + 7 × 64 КиБ; Table 5: bottom-boot SA0…SA7 по 8 КиБ).
Стирание «первого сектора 64 КиБ» стёрло бы только 8 КиБ — и это выяснилось бы
только на blank-check.

* голые имена `Am29DL322/323/642/643`, `MBM29DL322/642` теперь **отказывают**
  с подсказкой: раскладку задаёт суффикс T/B (Fujitsu — BE/TE), а «среднего»
  варианта у чипа нет;
* добавлены конкретные ревизии с картами из Table 3/5: `Am29DL322DB/DT`,
  `Am29DL323DB/DT`, `Am29DL324DB/DT`, `MBM29DL322BE/TE` — 8 × 8 КиБ + 63 × 64 КиБ
  (bottom) и зеркально (top), 4 МиБ, 3 В;
* `Am29PL320/640/1280` помечены как **не сверенные**: таких имён нет ни в
  `flashchips.h`, ни в `jedec_probe.c` — строка держалась на догадке.

И главное: проверка «две реализации не расходятся» раньше сравнивала только
ёмкость и карту секторов — и поэтому молчала, когда у одного и того же чипа в
пакете стояло 3 В, а в монолите 5 В. Теперь сверяются ещё напряжение, страница,
`wide` и `bypass`, и она сразу нашла восемь расхождений:

| Строка | Было | Стало |
|---|---|---|
| `Am29DL322/323/642/643`, `MBM29DL322/642` | 5 В в монолите, 3 В в пакете | 3 В (даташит) |
| `28F004S5`, `MBM29F016`, `MBM29F040C` | 3 В в пакете | 5 В (как у собратьев) |
| `Am29F016`, `Am29F040`, `Am29F080`, `SST39SF040`, `SST39VF040`, `Am29F200/400/800` | `bypass` включён с одной стороны | выключен: Unlock Bypass `20h` шлём только там, где это подтверждено даташитом (21444E5: «The device **now** has the Unlock Bypass Program feature» — то есть у ранних ревизий его нет) |

**Что нового в 2.17.5 — третий заход по таблице: сектор 128 КиБ и честные пометки.**

* **Macronix MX29F1610** — не «64 КиБ», а **16 секторов по 128 КиБ** (даташит
  16M-BIT [2Mx8/1Mx16]: «Sector erase architecture — 16 equal sectors of 128k
  bytes each», 5 В ±10%). Прежняя строка была опасна: команда стирания «одного
  сектора 64 КиБ» сносила блок целиком, то есть вместе с соседними 64 КиБ.
  Теперь это ловит и страж соседей, и сама таблица;
* **MX29F3210** — 32 × 128 КиБ по аналогии со MX29F1610, но даташитом не
  сверено, и это написано прямо в строке;
* строки, для которых не нашлось **ни даташита, ни таблицы** (ни `flashchips.h`
  flashrom, ни `jedec_probe.c` ядра), больше не выдают себя за проверенные:
  у них поле `unverified`, а отчёт печатает «ВНИМАНИЕ: параметры не сверены с
  даташитом». Это `HN28F010/020/100`, `LH28F010/020`, `D28F010/020`,
  `M28F008/016`, `M5M29F010/020` и `MX29F3210`. Стирать ими можно, но первый
  сектор лучше проверить на копии карты: врать в таблице дешевле не становится.

**Что нового в 2.17.4 — страж соседей и второй заход по таблице.**

Главное не в данных, а в защите: добавлен **страж соседей** при стирании.
Ошибка «в таблице 64 КиБ, а на железе блок 128 КиБ» по самому сектору не
видна — он стирается в любом случае. Теперь перед стиранием запоминаются
байты за обеими границами сектора, а после стирания проверяется, что они не
изменились; если изменились — отказ с адресом соседа и объяснением, что
модель микросхемы неверна. Проверка стоит два чтения на сектор.

По таблице нашлось ещё:

* **Toshiba TC58FVT160** — не «2 МиБ по 64 КиБ, 5 В», а top-boot
  `31×64K + 32K + 2×8K + 16K`, **3 В** (даташит TC58FVT160/B160A: VDD
  2.7–3.6 В, коды 98h/00C2h). В байтовом режиме адреса команд у него
  `AAAh/555h`, а не привычные `555h/2AAh` — это прямо написано в даташите;
* **TC58FVT320** такого обозначения нет: 32-Мбит часть — `TC58FVT321`
  (`63×64K + 8×8K`), она и добавлена;
* **Intel 28F010/28F020/28F256/28F512** (12 В, первое поколение) стираются
  только целиком («Bulk Erase» в каталоге Intel): команды Sector Erase у них
  нет, поэтому набор честно отказывается, а не шлёт `30h` в пустоту;
* **28F320** без ревизии — отказ: у `B3T/B` boot-блоки, у `J3/J5` блоки
  крупнее 64 КиБ, и «среднее» имя тут опаснее отказа;
* у отказа появилось поле `why`: причина может быть не «ревизия не указана»,
  а «микросхема вообще не умеет поблочное стирание» — текст теперь разный.

Запись на живой карте пока не подтверждена полностью: основная проверка ведётся на модели микросхем
(`tests/nor_model.py`). Набор об этом честно пишет в отчётах.
